# Dog Racing — original practice release

Reference: https://mohiogaming.com/games/racing/dog-racing, reviewed 2026-11-04. MOHIO advertises historical recorded race video, six/eight-runner fields, and fixed-odds markets. Salem's version is original real-time geometry and animation. No MOHIO footage, models, branding, odds, certification or software is reproduced. Open asset searches found no verified downloadable realistic animated greyhound suitable for this release; no third-party animal asset was imported. The locally bundled Three.js renderer is MIT licensed.

## Rules and storage

The existing `neon_hounds_3d` catalog key now displays **Dog Racing**. `/games/dog-racing` is authenticated and requires `DOG_RACING_PRACTICE_ENABLED=true` on the API. The same flag adds the DOG_RACING task to the practice worker. Financial admission for this key is unconditionally paused, independently of catalog flags.

Six dogs race every three minutes; eight every four. Entries close before a 45-second race, followed by 15 seconds of results. One immutable selection per member per race, 10–500 whole practice ETB. Winner, ordered first two/three, unordered first two, top three, lower/upper half and odd/even use the existing published uniform 90% racing math. Gross returns include stake, rounded down. No purchased, transferable or redeemable stakes, cash-out, bonus, jackpot or autoplay.

Dog Racing and Derby deliberately share the existing `derby_accounts` **racing practice balance** (initial 1,000). This is disclosed in the rules. No new cash balance, financial ledger entry, schema migration or database privilege is needed. Races, tickets, histories and commitments are isolated using the fixed server-side `hounds-` prefix; legacy Derby rows are all non-`hounds-` IDs. Both admission and every round/settlement/history query enforce the namespace. The browser cannot choose that namespace or supply odds.

Dog Racing commitments use `dog-racing-uniform90-v1`; existing Derby commitments remain unchanged. Rejection-sampled Fisher–Yates determines the private finish order. Only published current progress is used to animate; no future finish is sent before the result. Snapshot recovery and the worker settle each receipt once using existing row locks and database balance/receipt guards. A reload cannot double-debit an exact retry. Failed or stale requests disable entry; unresolved requests retain their receipt payload for an exact retry.

## Visuals and accessibility

The renderer was rebuilt in November 2026 (see `docs/releases/greyhound-realism-20261111/`). Each runner is one continuous, procedurally generated skinned surface (body, neck, long head, rose ears, legs, paws and tail) on a 31-bone skeleton, built in code from anatomical cross-sections at racing-greyhound proportions: deep keel, tight tuck-up, muscular hindquarters, slender forelegs. A cloth jacket on the same skeleton carries the runner number on both flanks. Coats (fawn, black, parti-colour, blue, red, white-and-black, dark and light brindle) are painted per vertex; a velvet sheen and fine hair bump replace the earlier plastic look on balanced/high quality.

Motion is a rotary gallop (left hind, right hind, right fore, left fore) with extended and gathered flight, lumbar flexion, body pitch and bounce, a stabilised head and a trailing tail. Paw targets are solved with two-link inverse kinematics; planted paws stay fixed on the sand. The stride is advanced only by distance the runner actually moved along its published position (stride length and frequency follow that speed), so held or delayed checkpoints stop the legs instead of letting them run ahead, and replay/reload re-anchor without a sprint. Runners lean into the left-hand bends. Nothing in the renderer changes progress, order, timing or results.

The course has a raked sand ribbon with worn lanes, a striped infield, running rails with the hare-rail cover, grille-door starting traps that open at the off and are wheeled clear before the finish, a finish line with the red disc and a photo-finish tower, the grandstand, floodlights and a distant tree line. A low afternoon sun casts soft shadows that follow the field; a camera-relative fill, sky reflections and contact shadows keep every runner readable. A small lure runs ahead on the hare rail and a few sand puffs mark hind-paw lift-off (balanced/high only).

Cameras (trackside rail, follow and aerial) solve their distance so every visible runner and its number fits the actual viewport, including portrait phones, and move on a critically damped spring with no overshoot or shake. A gate shot frames the numbered traps before the off. Runner numbers are sharp HTML chips in jacket colours above each dog, nudged apart when they overlap.

Reduced motion shows one still overview of the whole oval with the dogs in a single held running pose, no camera movement, no dust and no lure. Low quality uses fewer segments, no shadow maps (contact shadows remain), no reflections and matte materials. Rendering uses a pixel budget instead of a fixed device-pixel-ratio cap, so phones are sharp at desktop cost; it stops entirely when the course is scrolled away or the tab is hidden and drops to about 10 fps when nothing is moving. WebGL construction failure, draw failure or context loss still show the numbered SVG track with published positions, and recovery rebuilds a single canvas.

The models, motion and textures are original and generated at runtime; no scanned, purchased, downloaded or third-party animal asset is used. The renderer depends only on the already bundled MIT-licensed Three.js. Generated catalogue artwork (`dog-racing.webp`) remains decorative cover art, not a gameplay screenshot.

## Validation and release

PostgreSQL-compatible PGlite tests run the actual service and existing SQL guards, including a full 45-second settlement, exact retries, immutable picks, hidden outcomes, isolated histories/admission, suspended users and late entries. They serialize connections and do not establish native concurrent lock scheduling; the existing Derby native suite remains the concurrency coverage for the unchanged lock/receipt path. Geometry checks include finite poses, continuous track bends, bounded static mesh counts, disposal and planted paws moving backward during stance. UI tests cover ordered selections, review/confirmation, stale state, result/history, field changes and expanded view.

Unit tests cover the gait (footfall order, planted paws, inverse-kinematics reach, spine flexion), the skinned model and track, the world (published placement, stride only from travel, rewinds, leaning), camera framing on phone and desktop aspects, and the scene lifecycle. `scripts/review-greyhound-realism.mjs` drives a built loopback preview with synthetic fixtures for stills, states, performance probes and frame-exact clips. Browser checks so far ran in headless Chromium with SwiftShader software WebGL; physical phone GPU visual, frame-rate and thermal acceptance is still required. No real-money bets, deposits or withdrawals are part of validation.

Deploy API/worker with the practice-only flag, then web. Existing migrator/predeploy commands stay unchanged. Roll back by disabling the Dog Racing flag and restoring the previous pinned commit; retain all existing race/ticket records.
